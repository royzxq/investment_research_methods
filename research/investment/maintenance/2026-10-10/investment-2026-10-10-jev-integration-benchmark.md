# Jev 公告分流与财报定位：接入及真实对照

日期：2026-10-10，Asia/Shanghai。生成端：Codex。承接[二次复核](investment-2026-10-10-reading-optimization-jev-review.md)。本轮已完成代码、技能接入、真实 Jev 调用、默认 Codex CLI 语义对照与回归；没有重跑完整公司投研或修改投资 canonical/compact。

**结论：接入可以用于辅助排序和原文定位，不能用于减少必读范围。关键证据没有从候选或原文入口中丢失，但模型标签会漏掉需要展开的上下文。财报样本的语义判断步骤较快，公告没有耗时优势；两个样本的 Jev token 总数均更多，不能宣称全流程省 token。** 技能因此采用按需调用，已有精确定位或关键词足够时继续普通读取，不默认全本扫描。

## 1. 已落地能力

- `scripts/research_jev.py prepare`：校验候选 ID、公开属性、原文哈希/字符范围、披露截止、提取边界和框架版本，生成 MCP 批次。精确披露日未知时保留 null，仅在有抓取证据支持的可得上界满足截止时允许排序。无效项留本地回退，不截断正文、不删除记录。
- `finalize`：核对原始响应、请求绑定、实际模型、主题和 ID 完整性；输出各主题**全量**队列、独立回退队列、来源与原文入口。所有项目仍为 `unread/unverified`，研究完成状态仍为 false。
- `show`：分页查看队列/缺口或取得单个读取入口，不把审计文件中的整批正文重新打印进主模型；单项查询重新检查来源。读取命令含 root、哈希和范围，入口失效时重新定位或保留缺口。
- `scripts/research_jev_benchmark.py`：可复现构造完整公告标题/财报页清单，并对独立冻结 gold 计算候选保留、主题提示和证据包到达位置。
- 技能路由已接入 deep-research-auto 与 stock-research 的资料获取阶段，使用[操作说明](../../../../.agents/skills/deep-research-auto/references/jev-ranking.md)。不新增依赖，不改 Jev 密钥、模型配置或文件读取权限；正文由编排程序直接传 MCP，主模型只看小摘要与必要原文。

实际 Jev 响应版本为 `jev-1.13.0`；服务别名仍为现有 `jev-latest`，脚本按响应的具体版本校验，不把别名当版本缓存键。本轮禁用跨运行标签缓存。全部产物只创建，初版和修正版结果分开保留。

## 3. 关键证据有没有遗漏

**物理候选及访问：** 168/168 条公告、580/580 页均保留；18 个证据包所需 41 页全部在队列中。逐条实际执行带哈希的读取命令，41/41 与冻结原文逐字匹配，机器状态仍为未核验。这证明访问完整性，不等于模型已经理解或完成财务核验。[访问检查](evidence/jev-integration/gold-access-check.json)

**主题标签：** 第一轮 Jev 的直接 yes 仅覆盖公告 52/78 个金标主题对，以及财报 39/46 个必要页—主题对。关键词、规则和回退能补回一部分，但不能代替结构展开。

修正版队列中，恒瑞 H1 PDF66、PDF165 在 `licensing_payments` 主题下没有被关键词、模型或该主题回退标出，仍保留在完整队列，并可通过关联方主题及证据包关系找到。它们承担关联交易进展、关联主体等上下文作用，不能仅凭逐页“是否包含许可条款”判断就丢弃。同样，公告 A142（季度报告）的现金主题、A60（中期业绩公告）的治理主题未被这些局部提示覆盖；定期报告完整检查仍须由框架/输入清单独立要求。

因此，**只读 yes、`candidate_union_match`、某个排序层级或 Top-K 都会漏掉完整证据包。** 本次接口没有这些完成条件。完整队列、回退义务、非相邻附注、跨页表头、单位、否认范围和关键原文独立复核继续保留。报告类必读集合必须按框架和 required_inputs 建立，不能把本次示例关键词表当作完整投资规则。

## 5. 实际耗时与 token 对照

另做隔离语义判断微基准：两端接收相同材料及三个自足问题，只返回每项主题分数，不进行投资判断。公告使用完整 168 条；财报使用冻结的 41 个必要页加固定种子抽取的 12 个其他页，共 53 页。Codex 使用本机默认 CLI 设置，没有指定或修改模型；日志未返回可核实模型名，保留未知。所有输入 ID 恰好返回一次，分数结构验证通过。

|同一语义任务|默认 Codex CLI|Jev MCP|观察|
|---|---:|---:|---|
|168 条公告：输入 token|26,934|140,571|Jev 更多|
|168 条公告：输出 token|5,777|10,065|Jev 更多|
|168 条公告：实际墙钟|84.87 秒|90.47 秒|Jev 慢 6.6%|
|53 页财报：输入 token|58,564|93,427|Jev 更多|
|53 页财报：输出 token|1,820|3,286|Jev 更多|
|53 页财报：实际墙钟|46.27 秒|35.14 秒|Jev 快 24.1%|

Jev 每条候选是一次请求，问题说明随候选重复；Codex 在单个提示中处理整批，这是本次原始 token 总量增加的重要实现差异。公告输入加输出从 32,711 增至 150,636（+360.5%）；财报从 60,384 增至 96,713（+60.2%）。不同模型的 token 单位与定价不可直接视为同价成本，未估算账单或订阅额度。

这是各一次单步骤测试，时长包含各自 CLI/MCP 编排开销；不是纯模型推理延迟，也没有用重复随机化实验估计波动。Codex 缓存输入为 0，reasoning 已含在输出口径中，不再次相加。Jev 的 usage 只报告成功项目，失败项目是否产生额外计费未知。[原始计量摘要与逐主题标签结果](evidence/jev-integration/semantic-probe-comparison.json)

质量不能忽略：相同阈值只作诊断，未经概率校准。微基准中，公告金标主题直接命中 Codex 为 68/78、Jev 为 51/78；财报为 42/46、Jev 为 39/46。部分金标是完整上下文依赖，不直接出现题目关键词，不能把这些数字泛化为总体分类准确率；但它们清楚说明 Jev 不能替代主代理核验或作为排除器。

首次全量 Jev 测试耗时 288.40 秒（最多两个批次同时运行），成功项目报告输入 1,157,687、输出 46,023 token；出现 3 个单项服务错误，均保留并回退。单独公告耗时复测另有 3 个单项错误；未当作 no，也未隐去失败开销。这些错误均为服务返回 `Body has already been read`，本轮未修改全局 SDK 或密钥配置。

若未来用 Jev 替代一次主模型批量语义判断，可以转移该步骤的主模型负担；本轮并未实测完整投研净节省。净收益还要计入返回排序摘要、继续读原文、独立复核、回退和全团队用量，不能直接声称省下表中全部主模型 token。

## 6. 使用决定及验证

现行入口提供**按需辅助**：公告候选量大、确需语义分流时可用，但本次没有加速/总 token 收益依据；财报优先目录和关键词，歧义较多时对候选集合使用 Jev。首次完整框架阅读及所有必要证据义务保持不变，不把完整 580 页扫描作为默认动作。

验证记录：

- 整仓 504 项离线测试，502 项首次通过；两项进程清理检查仅因沙箱禁止 `ps` 未完成，经自动审批单独重跑后 2/2 通过。新增 Jev 和 benchmark 测试共 43 项包含其中。
- 独立前向验证累计 57 个 CLI 场景。三处 P2（自定义 root 的读取命令、畸形 MCP content、片段外提取乱码）均修复并独立复验；排序修正保留必读、完整候选和未读/未核验状态。
- 两个技能的 bundled `quick_validate.py` 通过；`git diff --check`、框架结构检查通过。后者不证明全部语义等价或投资有效性。
- 真实 Jev API、默认 Codex CLI 微基准和关键页读取均已实际运行。未重新核定远端版本、未重跑完整估值报告，未提交、推送、交易或对外发布。
